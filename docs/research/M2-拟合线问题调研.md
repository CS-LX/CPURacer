# M2 调研：拟合线贴顶 / 数据从哪来

**现象（2026-08-08 手工）：** ROI 红框正确（`cap=ok cols=1181`），青色拟合线贴在图**顶部**水平一条，而系统蓝线/填充在图**底部**（约 5% CPU）。同时 Overlay **整窗闪烁**。

---

## 1. 闪烁（已定位并修）

**根因：** `CaptureTick` 每 ~80ms 调用 `SuspendForCapture`（把 Overlay 甩出屏 / Hide）再 `ResumeAfterCapture`。人眼即闪。

**修复：**

- 去掉逐帧藏窗。
- `ScreenRoiCapture` 改为桌面 DC `BitBlt(..., SRCCOPY)`，**不加** `CAPTUREBLT`，使 layered WPF Overlay 通常不进入截图像素（见 MSDN BitBlt / CAPTUREBLT）。

**残留风险：** 个别 GPU/驱动上「无 CAPTUREBLT 仍吸入 layered 窗」——若复现，再考虑 WGC 排除本进程窗，而不是重新闪藏。

### 1.1 拟合线越跑越高（正反馈）

**现象：** 跟踪瞬间大体对齐，随后调试折线自己一点点升高。

**机制：** 青色调试线若仍进入截图，自上而下扫描会先命中描边上沿 → 每帧抬高约 1px → 缓慢爬升。

**对策（已做）：**

1. 调试折线改为**橙色**（非 Taskmgr 蓝）。
2. 列采样改为**自下而上**取最低连续填充带上沿。
3. `LooksLikeChartAccent` 要求 `B > G + 8`，排斥青/青色描边。

### 1.2 上下跳 / 高平台 + 向下刺（半透明填充）

**现象（多帧截图）：** 橙线常锁在偏高平台（约 20–30% 图高），夹杂向下尖刺贴近真蓝线；帧间上下跳。

**机制：** Win11 面积图在描边上方/填充内有**半透明蓝洗**；宽松「偏蓝即命中」会把模糊上沿当成地形，AA/合成每帧变化 → 部分列偶发打到真描边（向下刺）。

**对策（已做）：**

1. 按 `AccentScore` 找列内**高饱和描边脊**（非洗色顶）。
2. 列向只去 **impulse 尖刺**（勿用大半径 median——会把峰间谷填成高台并帧间闪）。
3. 重心只在 argmax±3 窗口内算，避免填充带宽在阈值附近时 thin/wide 两态跳变。
4. 取消宽松 `MatchesTheme` 爬填充。

### 1.3 重设计：拒绝坏帧，不再制造高台

多帧实测确认，橙线在「正确轮廓」与固定高度高台之间整帧切换。高台不是
真实图像特征，而是逐列未命中时使用 `plotH * 0.92` 固定回退值造成的。

当时的新流程（External 已于 2026-08-10 改为自研 WGC 只采 Taskmgr window +
`DWMWA_EXTENDED_FRAME_BOUNDS` 裁 ROI，并在 `StartCapture` 前关黄边；下述 WDA
仅保留在 Child 兼容路径）：

1. 对 Overlay HWND 设置 `WDA_EXCLUDEFROMCAPTURE`，从系统捕获层排除自身；
   调试框同时取消整面红色填充。
2. 每列只输出“可信描边候选”或 missing，**不再输出默认高度**。
3. 整帧可信覆盖率低于 25% 时判为合成中间帧并跳过，保留上一条可靠轮廓。
4. 局部 missing 段在左右可靠轮廓之间线性插值。
5. 仅修复单列 impulse，不使用会填平真实谷底的大半径 median。

这把算法从“独立逐列分类 + 人造回退”改为“整条轮廓的可信度与连续性恢复”。

## 2. 拟合线贴顶：原因假设（按可能性）

| # | 假设 | 说明 |
|---|---|---|
| A | **自上而下误匹配** | `SampleColumnTop` 从 plot 顶往下找「偏蓝」像素；若顶行网格/抗锯齿/标题底边被判为 accent，整列立刻返回 `y≈inset.Top` → 水平顶线 |
| B | **主题色过宽** | `MaxDistSq` 偏大，把深色底上微蓝噪点当填充顶 |
| C | **闪藏竞态（历史）** | 藏窗不完整时把上一帧青线/红底采进 ROI，强化错误顶线（修闪后应减弱） |
| D | **inset 不准** | 次要；主要导致整体平移， alone 不易造成「贴顶水平线」 |
| E | **坐标轴反了** | 绘制用 `YFromTop`；若误把「自底高度」当自顶 Y，线会翻到错侧——当前实现一致，优先级低于 A |

截图与 `cols=1181` 说明捕获与列循环在跑；问题在**颜色/边缘判定**，不是 ROI 跟丢。

**建议下一刀（实现向，非本次必做）：**

1. 托盘「转储一帧」：把 ROI BGRA 存 `docs/research/capture-m2-debug.png`，肉眼看采到的是蓝线还是灰顶。
2. 面积图改为**自下而上**找连续填充带上沿（或每列最大/最小 Y 的蓝色连通域顶）。
3. 收紧 hue/饱和度；排除低饱和网格。
4. 单测用「底蓝顶灰」真实色板，断言中心 Y 在下半区。

## 3. 要不要逆向 Taskmgr / 找源码 / 爬数据 / 上 C++？

### 3.1 官方源码

- 现代 **任务管理器不是完整开源产品**；Win11 性能页大量 **XAML + Composition / DirectUI**，折线在合成层绘制。
- 仓库里已有结论：`CvChartWindow` **BitBlt 只有网格、无蓝线**（[probe-results](probe-results.md) / 调研报告）。  
→ **没有**「打开 Taskmgr 源码抄一段 GetPolyline」的现实路径。

### 3.2 逆向（IDA/反编译/读命令缓冲区）

| 利 | 弊 |
|---|---|
| 理论上可找到内部点列或 VS 绑定 | 成本高、随版本碎、合规灰色、难维护 |
| | 蓝线在 DComp/GPU 路径时，静态分析收益差 |

**结论：** M2/M3 **不值得**作为主路径；仅当视觉拟合长期失败且 PDH 降级玩法也不可接受时再评估。

### 3.3 「爬数据」——PDH / 性能计数器

| 利 | 弊 |
|---|---|
| 稳定、文档化、`Processor\% Processor Time` 等 | **不是**屏幕上那条滚动折线的像素采样 |
| 可做影子山路 / 降级模式（计划 M4） | 相位、纵轴缩放、60s 窗口与 UI 滚动难像素级对齐 → **仍可能浮空** |

**结论：** 可作 **降级与日志对比**，**不能**单独满足「贴系统蓝线」硬规则（调研报告已写明）。

### 3.4 读窗 / UIA / Automation

- 本机 UIA 对 XAML 岛几乎无「CPU」名与 Selection；更无折线点数组。
- HWND 只给矩形，不给 series。

### 3.5 C++ 端查看

| 做法 | 评价 |
|---|---|
| C++ 里同样 Screen/WGC 采 ROI + 提边 | 与 C# **同类问题**，不自动更准；仅性能/藏窗策略可能更好 |
| C++ 注入 Taskmgr 读内存 | 高风险、违「不注入」约束 |
| C++ WGC 排除 Overlay 窗 | 合理工程加固，仍是视觉路径 |

**结论：** C++ 有价值在**捕获稳健性**，不是「换语言就拟合对」。

### 3.6 推荐主路径（仍坚持视觉合成帧）

```text
External：自研 WGC(只采 Taskmgr) → ExtendedFrame 裁 CPU ROI → 提边
Child：桌面 BitBlt(无 CAPTUREBLT) + WDA
  → Overlay 橙线验收
  →（可选）PDH 旁路只打日志
```

与立项硬约束一致：**碰撞山路必须拟合所见蓝线**。
