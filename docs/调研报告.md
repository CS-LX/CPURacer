# CPURacer 技术调研报告

> 版本：2026-08-08  
> 调研环境：Windows 11 家庭版中文版 Build **26200**，UI 语言 zh-CN，显示缩放约 **150%**（DPI 144）  
> 目标：评估在任务管理器「性能 → CPU」折线图上叠加赛车 meta 小游戏的技术可行性，并给出可执行的 PoC 路线。

---

## 1. 背景与问题定义

### 1.1 产品意图

CPURacer 希望把 **Windows 任务管理器 CPU 利用率折线图** 当成赛道：工作时 CPU 波动形成起伏「山路」，玩家开带物理的小车在上面行驶。这与 [copy-dialog-lunar-lander](https://github.com/Sanakan8472/copy-dialog-lunar-lander)（在资源管理器复制进度图上玩月球着陆）同属「寄生系统原生 UI」的 meta 游戏。

本仓库以 fork 子模块形式保留参考实现：`reference/copy-dialog-lunar-lander` → `https://github.com/CS-LX/copy-dialog-lunar-lander.git`（叙述与超链接仍指向原作者仓库）。

### 1.2 玩法规则（产品定义，驱动技术约束）

玩法会直接决定物理引擎、卷轴方向、碰撞体与「拟合」验收标准，故写入调研而非仅放 README。

| 规则 | 说明 |
|---|---|
| 山路 | 系统 CPU 折线（及面积上边缘）即地形；**视觉上必须贴合**用户所见蓝线，否则会出现「车在空中开」 |
| 物理 | 小车带刚体/简易车辆物理（重力、倾角、抓地）；可翻车 |
| 卷轴 | 折线图随时间 **向后（通常向左）滚动**；玩家须沿山路相对「向前」保持在图内 |
| 死亡判定 | **唯一死亡条件**：车被滚动带出视口（离开图表可见区） |
| 翻车 | 翻车本身不立即判死，但玩家失去有效操控，最终仍会被卷出视口 → 死亡 |
| Overlay | 只画车与必要 HUD；山路本体尽量使用系统图本身，避免自绘第二套山形抢戏 |

技术含义（后文展开）：高度场必须与合成帧蓝线同坐标系、同相位；卷轴速度与 Taskmgr 时间窗对齐；物理世界用地形法线而非「仅贴 Y」。

### 1.3 调研要回答的问题

1. 如何稳定找到 Taskmgr 及其 CPU 图区域？  
2. 如何得到与屏幕上蓝线**像素级可贴合**的「山路」高度场？（避免车浮空）  
3. 透明 Overlay 如何对齐、接收输入、处理 DPI/主题/切页？  
4. 安全与权限边界是什么？主方案与降级方案如何取舍？  
5. 是否已有「折线图上赛车」类开源先例可借鉴？

### 1.4 产品边界（本报告约定）

| 纳入 | 排除 |
|---|---|
| 外部进程透明叠加 | DLL 注入 / Hook Taskmgr 绘制 |
| 视觉贴合系统蓝线（主目标，玩法硬需求） | 仅 PDH 自绘假图作为**唯一**方案 |
| 默认标准用户完整性 | 强制要求管理员运行游戏 |
| 以 Win11 新版任务管理器为主 | Win10 经典 Taskmgr 双实现（仅对照） |

### 1.5 相关开源先例（检索结论）

未发现与 CPURacer **完全同构**（Taskmgr CPU 折线上开物理赛车）的项目。相近类别如下：

| 项目 | 关系 | 说明 |
|---|---|---|
| [copy-dialog-lunar-lander](https://github.com/Sanakan8472/copy-dialog-lunar-lander) | **最近的技术范式** | 系统原生进度图 + Overlay + 像素地形 + 物理；玩法是着陆而非赛车 |
| [ssjjul3/chartrunner](https://github.com/ssjjul3/chartrunner) | **最近的玩法范式** | 在 K 线/折线类图表上「跑酷/驾驶」；自绘图表，非 Taskmgr |
| [Vikramb1/moonshot](https://github.com/Vikramb1/moonshot) | 弱相关 | 价格线映射为街机角色纵向位置；非贴地赛车 |
| [markrussinovich/TaskManagerBitmap](https://github.com/markrussinovich/TaskManagerBitmap) 及 cpu-painter / TaskmgrPainter 等 | **反向先例** | 用 CPU 负载在 Taskmgr 上「画图」；是制造曲线，不是在既有曲线上玩游戏 |
| iRacing 类 telemetry overlay | 不相关 | 赛车游戏上叠图表，方向相反 |

结论：CPURacer 在「系统 UI 寄生」上对齐 lunar-lander，在「图表当跑道」上可参考 ChartRunner；**Taskmgr + 物理赛车** 组合尚无直接对标实现，拟合问题需自行攻关（见第 5 章）。

## 2. 参考项目解剖（可复用 / 必须重写）

参考工程：.NET Framework 4.7.1，WPF Overlay + WinForms 托盘，UI Automation + BitBlt 像素地形 + Box2D。

### 2.1 架构摘要

```text
托盘应用
  └─ OperationStatusWindowWatcher (UIA)
       └─ 发现 OperationStatusWindow → ChartView
            └─ OverlayWindow (透明 Topmost WPF)
                 ├─ CompositionTarget.Rendering 帧循环
                 ├─ WindowCapture.BitBlt → 高度场
                 └─ GameInterface.Update → 绘制/物理
```

关键源码：

| 能力 | 路径 |
|---|---|
| 窗口发现 | `reference/.../Source/CopyWatcher/CopyWatcher.cs` |
| Overlay / 高度场 | `reference/.../Source/GameOverlay/OverlayWindow.cs` |
| 游戏契约 | `reference/.../Source/GameOverlay/GameInterface.cs` |
| 截图 | `reference/.../Source/Utils/WindowCapture.cs` |

### 2.2 机制对照表

| 参考能力 | 参考做法 | 对 Taskmgr 的含义 |
|---|---|---|
| 发现图表 | ClassName `OperationStatusWindow` / `ChartView` / `RateChartOverlayWindow` | **必须重写**；本机实证为 `TaskManagerWindow` + `CvChartWindow` |
| Overlay 对齐 | 每帧读 UIA `BoundingRectangle` + `PointFromScreen` | **可复用思路**；DPI 与合成捕获需加强 |
| 高度场 | BitBlt 后按饱和色自底向上找「填充地形」 | **算法必须重写**：CPU 图是折线/面积图，且 BitBlt 往往**不含蓝线** |
| 世界尺度 | 约 395×85 DIU | Taskmgr 图更大且可缩放，需动态 `worldSize` |
| 输入/焦点 | Alpha=1 防点击穿透；失焦 `Top=20000` | **可复用** |
| 物理 | Box2D 着陆器 | **应保留物理引擎**（Box2D 或等价）：贴地、倾角、翻车；语义从着陆改为侧视卷轴赛车 |

### 2.3 可复用骨架 / 必须重写模块

**可复用（建议保留概念或直接移植骨架）：**

- 透明 WPF/`WS_EX_LAYERED` Overlay、`Topmost`、极低 Alpha 背景  
- `GameInterface` 式：`Init` / `HeightFieldUpdated` / `Update`  
- 托盘常驻、按前台窗口决定是否显示 Overlay  
- Per-Monitor DPI 意识（manifest + `GetDpiForWindow`）

**必须重写（标红）：**

1. **Watcher**：按 `Taskmgr.exe` + `TaskManagerWindow` + `CvChartWindow`（及页面状态）重写  
2. **捕获与高度场**：不能假设 BitBlt 得到地形色带；需合成帧捕获 + 折线/面积边缘提取，或 PDH 降级  
3. **世界与玩法语义**：由「底部地形着陆」改为「侧视卷轴山路赛车」——带物理、可翻车、出视口死亡；山路必须拟合系统折线

## 3. Taskmgr 窗口与「性能 → CPU」页发现

### 3.1 本机实证（方法 → 现象 → 结论）

| 方法 | 现象 | 结论 |
|---|---|---|
| `Get-Process Taskmgr` | 单实例 PID 存在 | **可行**：进程名语言无关，作第一锚点 |
| `EnumWindows` + PID 过滤 | 主窗 ClassName = **`TaskManagerWindow`**，标题「任务管理器」 | **可行**：ClassName 优于文案 |
| 子窗枚举 | 见 `DesktopWindowContentBridge`、`NativeHWNDHost`、`DirectUIHWND`、多个 **`CvChartWindow`** | **有条件可行**：现代 Taskmgr 是 Win32 壳 + XAML/DirectUI 混合 |
| UIA 按 ProcessId dump | 顶层可拿到主窗；深层 XAML `InputSite` 矩形常为无效；**图表 Name/AutomationId 多为空** | **有条件可行**：不要依赖中文 Name 作唯一键；用结构 + ClassName + 几何 |
| 多实例 | 本机 1 个进程 | 仍应按 PID 过滤，勿全局 ClassName 误匹配 |

原始记录：[docs/research/probe-results.md](research/probe-results.md)

### 3.2 定位策略建议

```text
1. 枚举进程 Taskmgr.exe
2. 找可见顶层窗 ClassName == TaskManagerWindow
3. 在子树中收集 ClassName == CvChartWindow
4. 取面积最大者作为主图候选（侧栏缩略图为小 CvChartWindow）
5. 用主窗客户区/UIA 辅助校验是否处于性能页（可选：检测侧栏多个小图并存）
```

**不要**把「CPU」「性能」等本地化字符串作为唯一条件；可作为启发式加分项。

### 3.3 页面状态

本机截图确认可处于「性能」且选中 CPU（侧栏缩略图 + 大图「% 利用率」）。切到「进程」等页时，大 `CvChartWindow` 可能消失或尺寸剧变——Overlay 应进入 Sleep。

Win10 经典 Taskmgr 类名/树可能不同；本报告不展开双实现，仅建议后续用版本探测分支。

## 4. CPU 图区域定位方案对比与实证

### 4.1 方案对比

| 路线 | 做法 | 优点 | 风险 | 本机结论 |
|---|---|---|---|---|
| A. UI Automation | 树遍历 + BoundingRect | 对齐方便 | Name/Id 空；XAML 节点矩形异常 | **辅助**，不能单靠 Name |
| B. Win32 子窗 | `CvChartWindow` | 有真实 HWND | 小图/大图需面积过滤 | **主定位手段（Win11）** |
| C. 客户区比例裁剪 | 按布局估矩形 | 不依赖控件 | 侧栏宽度/精简视图脆弱 | **降级** |
| D. 像素/OCR | 找「CPU」文字 | 不依赖树 | 贵、脆 | 备选 |
| E. 仅 PDH | 自绘赛道 | 稳 | 偏离「叠在系统蓝线上」 | **降级玩法** |

### 4.2 捕获实证

| 目标 | 方法 | 现象 | 结论 |
|---|---|---|---|
| 主窗 `TaskManagerWindow` | BitBlt / PrintWindow | 黑/空 | **不可行**（合成 UI） |
| 主窗 | `Graphics.CopyFromScreen` | 有内容（需前台） | **可行**（遮挡敏感） |
| 大 `CvChartWindow` | **BitBlt** | **仅灰白网格，无利用率曲线** | **部分可行**：能拿到控件 DC，但**蓝线不在 GDI 位图中** |
| 大 `CvChartWindow` | PrintWindow (PW_RENDERFULLCONTENT) | 失败 | 本机 **不可行** |
| 大 `CvChartWindow` 屏幕矩形 | CopyFromScreen | 能见到合成画面；非 DPI 感知进程坐标易错 | **有条件可行**：进程须 PerMonitorV2 |

证据图：

- [docs/research/capture-cvchart-load-bitblt.png](research/capture-cvchart-load-bitblt.png) — BitBlt 仅网格  
- [docs/research/capture-main-load-screen.png](research/capture-main-load-screen.png) — 前台整窗屏幕捕获含蓝线  

### 4.3 关键推论

> **参考项目「BitBlt(ChartView) → 像素地形」不能原样搬到 Win11 Taskmgr。**  
> `CvChartWindow` 的窗口 DC 主要是网格底图；利用率折线/填充由另一合成路径绘制。  
> 要贴合系统蓝线，必须使用 **屏幕/Desktop/Graphics Capture 合成帧**，或放弃像素贴合改用 PDH 影子赛道。

## 5. 赛道数据：视觉蓝线 vs 性能计数器

### 5.1 玩法数据需求（与「浮空车」问题）

物理车轮/车身碰撞依赖程序内 `heightField`（或折线 polyline）。若该山路与屏幕蓝线在 **位置、相位、纵轴比例、卷动速度** 任一维失配，玩家会看到：

- 车悬在蓝线上方（浮空）或陷入填充色下方；  
- 看起来贴线，但下一帧卷动后「滑落」；  
- 翻车判定与视觉坡度不一致。

因此：**「完全拟合折线图样式」不是锦上添花，而是本玩法的硬约束。** 降级影子赛道（PDH 自绘）可以玩，但不再满足「开在系统图上」的产品定义，只能作捕获失败时的后备。

### 5.2 拟合可行性分析

| 误差源 | 影响 | 严重度 | 对策 |
|---|---|---|---|
| BitBlt 无蓝线（本机已证） | 高度场来自错误图层 | 致命 | **必须用合成帧**（Graphics Capture / DPI 正确的屏幕 ROI） |
| ROI 裁剪含标题/边距 | 纵轴 0–100% 映射偏移 → 系统性浮空 | 高 | 标定绘图区（去「% 利用率」标题与底部署名区） |
| DPI / 物理像素错位 | Overlay 车与底层图错位 | 高 | PerMonitorV2；捕获与绘制共用同一物理矩形 |
| 主题色误检（网格/填充/描边） | 高度跳变、锯齿山路 | 高 | 优先追踪**折线描边或面积上边缘**；颜色容差 + 时间平滑 |
| Taskmgr 采样周期 vs 游戏帧率 | 相位滞后，车「追不上」坡 | 中高 | 环形缓冲按**图上时间轴**对齐；可短时外推，禁止用过期整帧 |
| PDH 与 Taskmgr 平滑策略不同 | 影子山与真线分叉 | 高（若当主路径） | PDH **不得**作主拟合源；仅校准/降级 |
| 面积半透明填充 | 自上而下扫色过早命中淡蓝 | 中 | 找每列「最上方实心主题像素」或边缘梯度峰值 |
| 逻辑处理器多图 | 多条曲线 | 中 | MVP 锁定总体利用率单图 |

**可行性结论：**

- **有条件可行**：在合成帧 + 正确 ROI + 边缘提取 + 与 Overlay 同坐标系的前提下，可将碰撞山路做到与蓝线视觉重合（目标：列向误差 ≤ 1–2 px，或相对图高 ≤ 1–2%）。  
- **不可行（作为主方案）**：仅靠 `CvChartWindow` BitBlt、或仅靠 PDH 重建山路，无法保证不浮空。  
- **验收建议（PoC M2）**：调试模式下把提取的 polyline 以半透明描边叠在系统图上；肉眼重合后再接物理车；用「车轮接触点 vs 蓝线采样」指标量化误差。

### 5.3 视觉追踪算法

参考算法假设「自底部向上的高饱和实心色带」。对本机 CPU 图：

| 方法 | 现象 | 结论 |
|---|---|---|
| 参考式 bottom-up fill | BitBlt 无色带；屏幕帧上也不稳定 | **不可直接复用** |
| 饱和色众数 + 自上而下找色 | 合成帧上可发现浅蓝系；阈值需按主题标定 | **有条件可行** |
| 面积图上边缘 / 折线描边检测 | 更贴合 Taskmgr 视觉与「山路表面」 | **推荐方向（拟合主路径）** |

算法草案（主路径）：

1. 捕获合成帧中大图 ROI（优先 Graphics Capture / 正确 DPI 的屏幕区域拷贝）  
2. 在 ROI 内估计主题色（蓝/强调色），容忍浅色/深色/高对比度  
3. 对每一列找「曲线上边缘」（面积填充顶边或折线像素），得到 `h[x]`，再转物理世界坐标  
4. 用环形缓冲表示与 Taskmgr 相同的时间窗；**横向卷速与图滚动像素/秒对齐**（可用相邻帧特征点相关估计）  
5. 网格线、坐标轴、文字用颜色距离 + 形态过滤剔除  
6. 对 `h[x]` 做轻度平滑（避免单像素噪声导致翻车），但平滑窗口过宽会「削峰」造成视觉与碰撞脱节——需折中

### 5.4 PDH / PerformanceCounter

本机采样 `\Processor(_Total)\% Processor Time`（丢弃首次 0 值）可稳定读到利用率。  

| 方法 | 现象 | 结论 |
|---|---|---|
| `PerformanceCounter` 1s 间隔 | 得到连续数值 | **可行**作数据源 |
| 与 Taskmgr 曲线像素对齐 | 平滑、周期、相位通常不一致 | **不能**单靠 PDH 声称「开在系统蓝线上」；**会导致浮空/陷地** |

**推荐组合：** 视觉高度场驱动物理山路与车辆；PDH 用于校准纵轴、检测捕获失败、驱动降级影子赛道（降级时应明确提示或改用自绘底图，避免「假贴合」）。

### 5.5 滚动与死亡判定的坐标语义

Taskmgr CPU 图是 **右进左出的时间卷轴**。与玩法对齐时：

- 世界 X 随时间向「路后方」卷动；车有自身速度/加速度，必须相对山路前进以留在视口内；  
- **死亡 = 车的 AABB/车身中心离开图表可见矩形**（非翻车瞬间）；  
- 翻车 → 失控 → 相对卷轴速度不足或轨迹异常 → 最终出界；  
- Overlay 只绘车；山路碰撞体与提取 polyline 一致，**不要另绘一条不同步的装饰线**（调试线除外）。

## 6. Overlay 渲染、输入、焦点与 DPI

### 6.1 渲染与窗口形态

推荐延续参考：**外部透明置顶窗** 盖在图表 ROI 上，只绘制车/特效/HUD，底下仍露出系统图。

| 技术 | 评价 |
|---|---|
| WPF `AllowsTransparency` + `CompositionTarget.Rendering` | 上手快，与参考一致，足够 MVP |
| Win32 `UpdateLayeredWindow` | 像素 Alpha 更可控 |
| Direct2D / DirectComposition | 高刷优化可后期再上 |

注意：背景 Alpha 必须 **≥ 1**，否则点击穿透无法操作。

### 6.2 输入与物理模型

- 油门/刹车/适度转向（侧视可简化为沿切线加速与跳跃抑制）；目标是在滚动山路上保持不翻车、不掉出视口  
- Overlay 需在 Taskmgr 前台（或用户明确置顶游戏）时接收键盘  
- 可参考失焦隐藏：移出屏幕而非仅 `Hide`，减少挡点击  
- 物理推荐 Box2D（与参考同栈）或轻量 2D 刚体：地形用 edge chain 跟随提取的 polyline，每帧/捕获周期更新顶点
### 6.3 DPI（高优先级风险）

本机 DPI 144。实证中：**非 DPI 感知的探针进程**用 `GetWindowRect` + `CopyFromScreen` 易错位（曾截到错误客户区内容）。

对策：

- 清单声明 `PerMonitorV2`  
- 统一用物理像素做捕获与定位，再换算到 DIU 布局  
- 跨显示器拖动做专项测试（参考项目已知 spasms）

### 6.4 捕获管线建议（主路径）

```text
每帧或 15–30Hz：
  更新 CvChartWindow / ROI 矩形（物理像素）
  Graphics Capture 或 Desktop 复制 ROI
  提取 heightField
  模拟步进 + Overlay 绘制
```

将 **捕获频率** 与 **模拟/渲染频率** 解耦，避免 120/144Hz 下过度 BitBlt/复制。

## 8. 安全、UIPI、完整性边界

| 问题 | 调研结论 |
|---|---|
| 是否注入 Taskmgr | **否**（排除路径） |
| Taskmgr 是否需当作 PPL | 一般不是 LSASS 级保护；仍勿注入 |
| 默认完整性 | 游戏 **asInvoker** 标准用户 |
| 管理员 Taskmgr + 标准用户游戏 | 可能触发 **UIPI**，UIA/部分跨进程操作失败 → 文档提示「请以相同完整性运行」或降级影子赛道 |
| 本机探针 | 非提升进程下 UIA 枚举 Taskmgr **成功** |

对外表述：叠加与读取公开 UI/性能数据，不修改 Taskmgr 二进制。

## 9. 备选架构与降级策略矩阵

| 架构 | 真实感 | 工程量 | 脆性 | 定位 |
|---|---|---|---|---|
| **A. 真叠 Taskmgr + 合成帧视觉赛道** | 最高 | 中高 | 中（UI 变更/DPI） | **主路径** |
| B. 真叠窗口矩形 + PDH 影子高度 | 中 | 中 | 较低 | **捕获失败降级** |
| C. 仿 Taskmgr 皮肤自绘 + PDH | 中低 | 中 | 低 | 自动化全面失败时 |
| D. DLL 注入绘制 | 高 | 高 | 高 + 安全风险 | **排除** |

降级触发器示例：连续 N 帧 ROI 捕获失败、主题色丢失、UIPI 异常、找不到 `CvChartWindow`。

## 10. 风险、兼容性、PoC 里程碑与推荐技术栈

### 10.1 主要风险

| 风险 | 缓解 |
|---|---|
| Win11 功能更新改 UI 树 | 版本探测 + `CvChartWindow`/几何多策略；启动自检探针 |
| 蓝线不在窗口 DC | 合成捕获为主，BitBlt 仅辅助网格/ROI |
| 多显示器 DPI | PerMonitorV2；物理像素管线 |
| 高刷新率 | 捕获限频 15–30Hz |
| 本地化 | 进程 + ClassName + 几何，文案只作启发式 |
| 遮挡 | 屏幕捕获需 Taskmgr 可见；被挡则 Sleep 或改用 PDH 降级 |
| 参考 HWND 截断为 `int` | 全项目使用 `IntPtr` 完整句柄 |

### 10.2 推荐技术栈（唯一主推荐）

- **语言/UI**：C# / .NET（WPF 或 WinUI 3），托盘常驻  
- **发现**：`Taskmgr.exe` + `TaskManagerWindow` + 最大 `CvChartWindow`（UIA 辅助）  
- **赛道**：Windows Graphics Capture 或 DPI 正确的屏幕 ROI 复制 → 折线/面积上边缘 → `heightField`  
- **校准/降级**：PDH `\Processor(_Total)\% Processor Time`  
- **游戏**：2D 物理卷轴赛车（建议 Box2D）；碰撞体 = 视觉提取 polyline；死亡 = 出视口  
- **清单**：`PerMonitorV2`，`asInvoker`

### 10.3 不可行 / 不推荐项清单

- 原样复用 `OperationStatusWindow`/`ChartView` 类名与 bottom-up 地形算法  
- 仅对 `CvChartWindow` BitBlt 提取利用率曲线（本机证明无蓝线）  
- 注入 Taskmgr  
- 无 DPI 感知的屏幕坐标捕获  
- 仅用本地化标题定位页面  

### 10.4 PoC 里程碑

| 里程碑 | 目标 | 完成标准 |
|---|---|---|
| **M1** | 钉住 CPU 大图矩形并跟随 | Overlay 框与大图重合，拖动/缩放正确 |
| **M2** | 稳定提取滚动高度场并**可视拟合验收** | 调试描边与蓝线肉眼重合（目标 ≤1–2% 图高误差）；卷速对齐 |  
| **M3** | 物理车上线可玩原型 | 贴地行驶、可翻车失控、出视口死亡、基础重开 |
